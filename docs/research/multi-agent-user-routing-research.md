# 多 Agent 用户路由：意图变更、上下文转移与前缀复用的应用实践

> 状态：行业调研笔记，不是本仓库的实现方案或代码审计。
>
> 调研日期：2026-07-31。产品行为会变化，采用前应复核原始资料。
>
> 核心问题：在一个由会话入口 Agent 协调、可路由到多个专门 Agent 的系统中，用户在任务已被委派后改变意图时，系统如何重新判定任务关系、重路由、重组上下文，并尽可能复用稳定提示前缀。
>
> 范围：已上线的多 Agent 应用及其公开工程资料；长任务的打断、上下文隔离、交接和稳定前缀复用。
>
> 不在范围：本地 coding agent、通用多 Agent 框架/SDK/API 的功能罗列、任何产品的私有分类器或本仓库的落地设计。

## 1. 结论

- **先判断新消息与活动任务的关系，再选目标 Agent。** "继续"、"把条件改成 B"、"顺便做一个独立检查"、"停掉这个，改做 C" 不是同一种路由请求；按孤立主题直接映射 Agent 会把修订、替换和取消误判成同类请求。[综合推论]
- **协调状态应始终可见，但主 Agent 不必处理每一轮对话。** Claude Research 的 lead-worker、Manus 的 controller-worker，以及 Copilot Studio 的 parent/connected-agent 都把协调与执行分开；明确 handoff 后，用户可直接与专门 Agent 对话，由路由 Agent 根据新的语义和任务图动态决定何时重新协调。[A][B][C][综合推论]
- **上下文不是整段聊天记录。** 已公开产品展示了三种不同取舍：默认传递会话历史（Copilot Studio）、给并行 worker 干净上下文（Manus）、以外部 memory、摘要和工件引用保持连续性（Claude Research）。这说明全量复制历史不是普遍默认，也不是唯一正确策略。[A][B][C]
- **用户中途改意图时，应先停止旧任务的后续调度，再决定是否保留旧结果。** 旧 worker 的晚到结果只能作为可追溯候选证据，不能自动变成新任务的结论；“中断”也不能被理解为已经回滚外部副作用。[综合推论；公开产品未披露完整取消语义]
- **前缀复用首先是应用层的语义复用。** 将稳定的政策、角色合同、任务锚点和工件引用按块重编，才能跨路由复用而不携带过期意图。主流应用公开资料很少披露底层计算复用，因此不能把任何缓存效果当作本研究的事实或正确性前提。[综合推论；公开证据缺口]

### 证据标记

- **公开事实**：可以从链接中的产品页面或工程文章直接核验。
- **综合推论**：从多个公开事实归纳出的系统处理方式，不宣称是任何厂商的私有实现。
- **未公开**：公开资料没有足够证据，不用产品 UI 或营销描述补全内部细节。

## 2. 可观察的应用实践

以下案例只把已公开的行为当作证据，不把未披露的内部路由器、取消协议或缓存实现写成事实。

### Claude Research

- **公开事实：** 用户请求由 lead agent 分析和制定策略，再并行创建专门 subagent；每个 subagent 在独立上下文中研究并向 lead 返回结果。[A]
- **上下文实践：** lead 会把研究计划存入外部 memory；长对话中会总结已完成阶段，必要时以干净上下文的新 subagent 和谨慎 handoff 维持连续性；大输出可留在持久工件中，只回传轻量引用。[A]
- **未公开：** 用户在 worker 运行时发送新目标后，系统如何分类、取消或合并结果。文章还明确说 lead 当前同步等待每批 subagent，因而不能 steer 子 agent。[A]

### Manus Wide Research

- **公开事实：** 主控制器把大量独立项目拆成并行子任务；每个 worker 是完整 Manus 实例，拥有独立 VM、工具环境和空上下文；协调经主控制器集中完成。[B]
- **上下文实践：** 公开材料把干净上下文、worker 间不直接通信和主控汇总作为降低上下文污染、隔离错误的手段。[B]
- **未公开：** 用户对运行中任务提出修订、替换或取消时的路由和状态语义；其效果描述属于 Manus 的产品自述，不是普遍实证结论。[B]

### Microsoft Copilot Studio

- **公开事实：** parent agent 可以调用 child/connected agent；connected agent 有各自编排、工具、知识和 transcript，平台建议由 parent 统一对用户回复。[C]
- **上下文与后续消息：** 文档称跨 agent 调用默认传递对话历史，同时要求显式管理 handoff 数据；若子 agent 预期用户继续回答，使用 ask 维持该对话，使用单向 inform 后的用户回复会回到 parent planner 作为新查询。[C]
- **边界：** 这是企业产品的公开配置/运行指南，不是其内部意图分类算法；不能据此推断所有产品默认全量传递历史。

### ChatGPT Deep Research

- **公开事实：** 这是用户可见的长时、多步骤研究产品；官方页面没有把其内部架构声明为多 Agent。[D]
- **意图变更信号：** 用户可以实时跟踪进度，并 interrupt 后用后续提示或新来源 refine 研究。[D]
- **边界：** 它只提供“用户意图变更”的交互证据，不能证明其内部的多 Agent 路由、上下文包或 worker 取消机制。

**从案例能确认的共性。** 并发来自可拆分且相对独立的任务，而不是关键词命中；协调者负责拆分、汇总和用户关系；worker 的输入需要有边界。Claude Research 还明确要求子任务包含目标、输出格式、工具/来源指南和边界，以减少遗漏和重复。[A]

**从案例不能确认的内容。** 没有找到主流应用公开其完整的“意图变化分类器”、运行中 worker 的精确取消确认协议、迟到结果的自动合并规则，或跨不同 Agent 的底层前缀计算复用方式。后文涉及这些问题时均为综合模型，而非厂商事实。

## 3. 应把“智能路由 Agent”“对话 owner”和“运行时校验”分开

以下是由上述实践归纳出的参考模型。核心应是一个能读取全局任务状态、理解长对话语义的**路由 Agent**，而不是按关键词或固定分支转发消息。每条用户消息由它形成新的任务图判断；主 Agent、当前 specialist 或多个新 worker 都可能成为下一步接收者。[综合推论]

| 角色 | 职责 | 是否必须在每轮生成回复 |
| --- | --- | --- |
| 路由 Agent | 理解新消息相对全局任务图的含义，生成任务图增量和路由计划 | 不必；它可只做一次短推理并把消息直送目标 Agent |
| 对话 owner | 与用户进行当前连续对话，可能是主 Agent，也可能是已 handoff 的 specialist | 只有它被路由计划选中时才需要 |
| 运行时控制面 | 保存事件、执行路由计划、校验权限/预算/并发/副作用边界 | 否；这是确定性的执行与约束层 |

```text
用户新消息 + 全局任务图 + 各 Agent 的活动摘要
  -> 路由 Agent 的语义推理
  -> 任务图增量 + 路由计划
  -> 运行时校验可执行性
  -> 当前 specialist | 新 specialist | coordinator | 并行 worker
  -> 直接回复用户，或回传工件 / 结果
```

这意味着“经过主 Agent”不是固定步骤。显式 handoff 后，路由 Agent 可以继续把后续消息直接送给该 specialist；当其判断目标、优先级、能力边界或上下文依赖已经变化时，再将消息送到适合协调全局任务的 Agent。

协调控制面至少要能查询五类不同的对象；它们不应被混成一个不断增长的 prompt：

| 对象 | 作用 | 是否直接完整注入给下游 Agent |
| --- | --- | --- |
| 对话账本 | 保存原始用户消息、回答、路由和工具事件的顺序 | 否；按当前任务取相关片段 |
| 任务快照 | 当前目标、约束、验收条件、计划和哪些内容已经失效 | 是；但只给与当前任务有关的投影 |
| 路由 / 运行状态 | 当前对话 owner、handoff 模式、待回答问题、正在运行的 worker、取消和完成状态 | 只给会影响本次工作的部分 |
| 工件与副作用状态 | 资料、文件、来源、已提交动作及其真实状态 | 用引用或必要摘要，不默认复制全文 |
| 编译后的上下文包 | 某个接收者本次实际可见的输入 | 是；它是临时输入，不是权威事实账本 |

这也解释了为什么“当前对话由哪个 Agent 处理”不能只存为一个 topic 标签：同一主题下，用户可能正在回答某个 specialist 的追问，也可能是在叫停这个 specialist 并换一个目标。前者可直达当前对话 owner，后者必须触发重路由。

## 4. 用户意图变更后的重路由

### 4.1 识别的是相对关系，而不是单独主题

路由 Agent 应同时看新消息、活动任务图、当前 pending question、各 worker 的活动摘要和已发生的外部动作，并在这些信息上做语义推理。它的输出不是单一的 topic 标签，也不必落入一个互斥枚举；一条消息可以同时修订任务 A、创建任务 B，并降低任务 C 的优先级。[综合推论]

路由 Agent 的产物应是一组**图操作**：它可以更新某个任务的约束、建立新任务和依赖、暂停或降低旧任务优先级、绑定一段回复到某个 pending question，或改变谁暂时面向用户。一条消息可以产生其中的多个操作；这些操作由语义推理生成，而非从预设标签表中挑选。

`destination`（哪个 Agent）和 `delivery`（它是一次性咨询、后台 worker，还是新的对话 owner）在任务图更新之后再分别决定。Copilot Studio 对 ask 与 inform 的区分说明：即使子 Agent 已参与当前工作，下一条用户消息是否继续落到它，仍取决于互动状态和产品协议，而不是“此前主题属于它”。[C]

### 4.2 意图识别的语义过程

公开应用没有披露完整分类器；Claude Research 只公开了 lead 会分析请求、制定策略并拆分子任务，Manus 只公开了主控制器会理解任务结构和依赖。[A][B] 以下过程因此是针对该公开缺口的综合模型：它把意图识别视为一次受上下文约束的规划推理，而不是训练一个孤立的 topic classifier。

路由 Agent 的语义依据至少来自五个方面；这些是推理输入，不是把消息写死为关键词规则：

| 语义依据 | 它解决的问题 |
| --- | --- |
| 用户的原始措辞 | 识别目标、否定、比较、时序、优先级、范围和显式交付偏好 |
| 指代与对话行为 | 判断“这个”“刚才的问题”“另外”等词指向的任务、工件或 pending question |
| 任务图 | 理解任务之间的父子、依赖、冲突和完成关系，而非只看最近一句话 |
| Agent / 执行状态 | 区分当前对话 owner、后台 worker、已暂停任务和已发生的副作用 |
| 用户与组织约束 | 理解长期偏好、权限边界和用户刚刚撤回或新增的限制 |

**第一步：构造路由 Agent 的观察面。** 它不需要携带每个 worker 的完整对话，而需要看到当前任务图的紧凑卡片：每个活动任务的目标、约束、owner、状态、最近的关键结论、pending question、相关工件和副作用。对于很长的会话，还应按用户提及的实体、时间线、显式引用、近期性和语义相关性取回候选任务；检索只缩小观察面，不替代最终理解。

**第二步：从一条话中分解多个意图原子。** 路由 Agent 识别用户是在陈述目标、回答问题、否定先前结论、增加约束、改变优先级、授权/撤权，还是创建新工作。它还要做指代消解和时序判断，例如“这个”“刚才那个”“改为”“先不要”“另外”分别指向什么，以及哪个要求覆盖哪个旧要求。

**第三步：把意图原子对齐到任务图。** 模型将每个原子与一个或多个已有任务、worker、工件和 pending question 建立语义边：可能是支持、修订、冲突、替代、回答、依赖或新建。相似度只能提供候选；“不要继续代码，但保留调研结论”这种否定与保留并存的关系必须由模型结合任务状态理解。

**第四步：生成并比较路由假设。** 路由 Agent 可以提出不止一个计划，例如“保持当前 specialist”“当前 specialist 继续，同时创建一个合规任务”“暂停旧任务后整体换 owner”。比较的对象是对所有意图原子的覆盖度、上下文是否足够、任务依赖、预期工具能力和用户体验，而不是某个单一类别的概率最高。[综合推论]

**第五步：保留不确定性。** 当两个解释都会显著改变任务、成本或副作用时，路由 Agent 应把候选解释和缺失信息交给用户确认，或调用更强的协调 Agent 再推理；不要把低把握的单一路由伪装成确定理解。

下面是复合意图的示意，而非固定规则：

| 用户消息片段 | 语义对齐 | 任务图变化与可能路由 |
| --- | --- | --- |
| “回答数据专家刚才的问题” | 回答当前 pending question | 保留数据任务，可直接给数据 specialist |
| “别再改代码” | 撤回写入类工作的授权 | 标记相关写入任务受限或暂停，控制面阻止后续提交 |
| “另外比较合规方案” | 创建独立目标 | 新建合规任务，交给合规 specialist，并与数据任务并行 |

这三个变化来自同一条自然语言消息；把它压缩成一个 `replace`、一个 Agent 名或一个关键词路由，都会丢失用户意图的一部分。

### 4.3 路由 Agent 应产生“任务图增量”，而非固定分类

上一节的语义理解只有被写成可追溯的任务图增量，才不会在后续路由时退化成一段不可验证的自然语言摘要。它表达的是：用户现在真正想推进、修改、暂停或比较哪些工作线；哪些工作线应继续存在；谁最适合承担每一部分；以及哪些上下文仍然有效。[综合推论]

一次推理的输出应能够同时表达以下内容：

- 对已有任务的修改、降级、终止或优先级调整；
- 新任务和依赖关系，而非只能选择一个现有任务；
- 每个任务的候选 owner、是否需要直接对话、并行还是等待；
- 需要复用、失效或按需读取的上下文和工件；
- 不确定项，以及是否值得向用户发起一个澄清问题。

对于跨任务、会修改状态或存在多个合理解释的消息，可以让第二个审阅 Agent 检查该计划：是否覆盖了用户的每个意图片段，是否漏掉否定/优先级变化，是否把相互冲突的任务同时标成当前目标，以及每个接收者是否拿到了足够且不过量的上下文。它审的是语义计划而不是固定规则；出现分歧时保留多个候选路由或询问用户。[综合推论]

例如，用户说“先回答数据专家刚才的问题；另外把合规风险单独评估一下，原来的市场研究先别继续”时，智能路由不应强行选一个 `continue` 或 `replace`：它可以把第一部分直接给数据专家、创建合规 specialist 的独立任务，同时暂停市场研究。这个结果来自语义分解和任务图更新，不来自关键词规则。[综合推论]

显式的“停止”“改由 X”“不要写入”等信息仍然是强约束或强证据，但它们只限制路由 Agent 可提出的计划。权限、预算、并发和不可逆操作由运行时在计划之后校验；运行时不代替路由 Agent 理解用户意图。

### 4.4 是否直达当前 specialist，应由路由 Agent 动态决定

直接 handoff 是一种可撤销的对话状态，而不是把会话永久粘在某个 specialist 上。路由 Agent 应综合判断：

- 新消息是否主要延续当前 specialist 的任务和它正在等待的回答；
- 当前 specialist 的上下文、能力和工具是否仍足以完成用户想要的结果；
- 消息是否同时引入了跨任务依赖、新的并行机会或全局优先级变化；
- 当前 specialist 的继续是否会遗漏用户刚表达的否定、范围或风险要求；
- 让 coordinator 参与是否能带来更好的拆分、汇总或用户体验。

因此，路由 Agent 可以选择直接转交、让 coordinator 先更新任务图后再转交、同时投递给多个 Agent，或先问一个澄清问题。主 Agent 只是这些候选接收者之一，并非每轮必经中转站。Copilot Studio 的 ask/inform 行为说明“继续留在 specialist 对话”本身就是一个显式的交互协议，而不是主题粘性。[C]

### 4.5 旧 worker 和晚到结果

公开资料尚不足以说明任何上述产品在此处的精确内部行为。一个可审计的通用处理是：替换或取消时停止未来调度，向可取消的运行单元发送取消；新任务不等待旧结果才能开始；旧结果带着其输入任务版本/上下文包标识回传，只有在当前任务仍明确引用它时才被采纳，否则仅归档为候选证据。[综合推论]

这条原则尤其适用于会产生副作用的工具：取消请求不代表文件、消息、付款、云资源或数据库写入已经没有发生。系统应查询或展示实际终态，而不是把 UI 的“停止”解释为回滚承诺。

## 5. 重路由时上下文怎样改变

### 5.1 保留事实账本，重新编译每个 Agent 的输入

Manus 倾向于让 worker 从干净上下文起步；Claude Research 用外部 memory 和工件引用跨窗口维持连续性；Copilot Studio 默认传递历史但要求管理 handoff 数据。[A][B][C] 这不是单一标准答案，而是说明上下文应随任务关系和接收者改变。

重路由后的最小上下文包通常包含：

- 接收者的职责、允许工具和预期输出；
- 新用户原文，以及当前生效的目标、约束和验收条件；
- 本次变化相对旧任务的关系，例如“替换”或“仅新增一个独立子任务”；
- 与新目标直接相关的工件、来源和已验证结论的引用；
- 正在执行或已经发生的副作用状态；
- 必要的早期摘要，并明确其覆盖范围和已失效内容。

通常不应默认转移：无关历史、其他 worker 的私有 scratchpad、完整工具日志、已撤销的计划/权限，以及未经核验的长期记忆。原始记录可以保留在账本中供审计，但“保留”不等于“继续放进模型输入”。[综合推论]

### 5.2 四种变化的上下文差异

| 变化 | 应复用的语义信息 | 必须新建或重算的部分 |
| --- | --- | --- |
| 继续 | 当前任务目标、未完成步骤、最近工件和待回答问题 | 新用户消息及最新运行结果 |
| 修订 | 未受影响的事实、来源和已完成工件 | 被否定的约束、受影响计划、验收条件和相关 worker 的任务合同 |
| 扩展 | 父任务的稳定事实、明确依赖和输出格式 | 独立子任务的目标、工具范围、结果合同和隔离边界 |
| 替换 / 取消 | 可复用证据与真实副作用状态 | 新目标或取消范围；旧计划不再作为当前指令 |

如果用户正在回答一个 specialist 的明确问题，路由 Agent 可以把回答作为该 specialist 的局部续写；若消息同时改变了目标、权限、范围或其他任务线，路由 Agent 应更新任务图后选择新的接收者。这个“局部续写还是全局重路由”的判断来自 pending question、任务关系和整体目标的联合语义，而不应只由最近发言者或固定规则决定。[综合推论；Copilot Studio 的 ask/inform 行为提供了交互层面的佐证][C]

## 6. 如何复用稳定前缀而不复用过期意图

### 6.1 本文的“前缀”是可重编的语义块

已公开的应用资料能证明 memory、摘要、干净 worker 上下文和工件引用的存在，却很少披露底层模型是否、如何在不同 Agent 之间复用已处理的前缀计算。[A][B][C] 因此本文只讨论**应用层前缀复用**：上下文编译器复用稳定、可追溯的信息块，而不是假定底层一定复用某段输入计算。

这种复用的单位不是完整 prompt，而是有来源和作用域的内容块。例如，同一个组织政策、同一个 specialist 合同、同一个未被推翻的任务事实，可以在多个后继上下文中重复引用；最新用户意图、路由计划和运行状态则每轮重新生成。[综合推论]

### 6.2 分层：稳定信息在前，当前意图在后

```text
[平台稳定块] -> [Agent profile 块] -> [任务锚点块] -> [本轮意图与运行态]
      最稳定          按角色稳定          按任务稳定             每轮重编
```

- **平台稳定块**：固定安全规则、通用工具说明、格式约束和可信数据边界。
- **Agent profile 块**：当前接收者的职责、反职责、可见工具和输出合同。不同 specialist 有不同 profile；不能因它们处于同一会话就把角色语义混用。
- **任务锚点块**：经过确认的目标、未被否定的事实、关键工件和依赖索引。它是路由 Agent 和执行 Agent 共同理解任务的基线。
- **本轮意图与运行态**：新用户原文、路由 Agent 生成的任务图增量、当前有效的覆盖/否定条件、pending question、取消状态和最新结果。它必须以本轮为准。

任务锚点应当可以重建而不是无限追加补丁。用户连续修订时，可保留原始 brief 作为历史证据，但需要生成新的“当前任务锚点”来表达真正生效的目标；否则旧目标虽然仍在上下文前部，却会持续干扰后续 Agent。[综合推论]

### 6.3 路由 Agent 和执行 Agent 复用不同前缀

路由 Agent 需要的是**全局但稀疏**的前缀：稳定规则、路由职责、活动任务卡片、任务之间的关系和各 worker 的状态摘要。它不应读取所有 specialist 的完整对话，否则重路由本身会被无关细节淹没。

每个执行 Agent 需要的是**局部但更深**的前缀：稳定规则、自己的 profile、所负责任务的当前锚点、必要工件和本轮任务图增量。direct handoff 持续时，这个局部前缀可以沿用；一旦路由 Agent 将用户目标绑定到别的任务或角色，新的执行 Agent 从自己的 profile 和新的任务锚点开始，而不是继承旧 specialist 的全部上下文。[综合推论]

因此，多 Agent 系统应复用“可证明相同的语义块”，而不是试图让所有 Agent 共用一份不断扩大的会话前缀。Claude Research 的外部 memory/工件引用和 Manus 的独立空上下文，是这种分层思路的两个公开应用案例。[A][B]

### 6.4 路由变化如何决定复用与重编

| 路由变化 | 可复用的稳定块 | 必须重编的上下文 |
| --- | --- | --- |
| 当前任务继续 | 平台、当前角色、任务锚点和相关工件 | 最新消息、最新结果和下一步计划 |
| 用户修订约束 | 平台、角色、未受影响的事实和工件 | 当前任务锚点中受影响部分、否定/覆盖关系和受影响 worker 合同 |
| 新增并行任务 | 平台、必要的父任务事实和共享工件 | 新任务锚点、新 specialist 合同、独立输出边界 |
| 替换主目标或换 owner | 平台、经路由 Agent 判定可复用的证据、真实副作用状态 | 新角色 profile、新任务锚点、当前目标和旧任务的历史化说明 |

一个有用的交接产物是简短的**过渡胶囊**：它只记录新消息与旧任务的关系、仍有效的事实、明确失效的决策、正在发生的副作用和可按需读取的工件。新的 Agent 不需要把旧会话全文塞进输入，路由 Agent 也能据此解释为什么这次是续写、分支还是替换。[综合推论]

若底层模型恰好优化重复前缀，它只能被视为这种稳定内容布局可能带来的附带收益。应用不应承诺跨 Agent 的底层复用，也不应把任何复用标识当作租户隔离、访问授权或任务版本的唯一标识；这些均属于公开产品资料尚未给出的内部合同。

## 7. 容易出错的假设

| 错误假设 | 后果 | 更稳妥的理解 |
| --- | --- | --- |
| “新话题 = 必须换 Agent” | 将修订和取消误路由，用户关系不断抖动 | 先判断与活动任务的关系，再选 destination 和 delivery |
| “此前 worker 就是下一轮 owner” | 用户的替换目标仍被旧 specialist 吞掉 | 由路由 Agent 根据任务图、当前互动和新目标动态选择；当前 worker 只是候选之一 |
| “交接就是传全部历史” | token 膨胀、无关信息泄露、旧计划压过新目标 | 账本完整保存，按接收者编译最小上下文包 |
| “取消 = 没有发生” | 外部副作用和晚到结果被错误隐藏 | 取消后查询实际状态，旧结果默认不自动合并 |
| “稳定前缀可复用 = 可以沿用旧 prompt” | 过期目标或权限被稳定地重复注入 | 只复用稳定语义块；当前目标和覆盖条件始终后置、可重建 |
| “产品有停止按钮 = 已知其 worker 语义” | 将 UI 行为外推为内部一致性协议 | 明确记录公开缺口，并用测试验证实际产品合同 |

## 8. 应验证的开放问题

- 实际产品对“正在运行时用户改目标”的响应时延、是否允许跟进消息排队、以及对各类工具的取消确认边界。
- 当用户回复一个 specialist 的澄清问题，同时附带新目标时，产品如何在局部续写和全局重路由之间判定优先级。
- 相同语义块在跨角色、跨会话或跨 worker 时能否复用到何种程度；主流应用通常不公开底层计算复用、保留期和隔离范围。
- 摘要或 memory 被用户否定后，系统如何标记失效、重新生成和避免它在后续路由中被当作事实。
- 评估不应只测首次 topic 分类。至少覆盖：修订上一结论、替换运行中任务、取消后晚到结果、独立扩展并行执行、回答 specialist 追问、切换角色后缓存失效与重建。
