# 权限模式快捷切换：业界实践

> 状态：调研笔记，不是实现设计或迁移方案。
>
> 调研日期：2026-08-10；采用前应重新核验。
>
> 范围：交互式 coding agent 在会话中切换工具权限模式时的可见性、硬拒绝规则与高权限提示。
>
> 不在范围：任何具体产品的未公开快捷键实现、组织策略、或本仓库的实现映射。

## 1. 结论

- **事实：** OpenCode 把工具权限规则分为 `allow`、`ask` 和 `deny`，并提供自动批准模式；显式 `deny` 规则在自动模式下仍被执行。[OpenCode permissions](https://opencode.ai/docs/permissions/)（访问日期：2026-08-10）。
- **综合：** 快捷切换权限模式必须让当前模式在 UI 中持续可见，并且不应绕过不可变的硬拒绝或路径保护；否则用户难以区分“自动批准”与“取消安全边界”。
- **综合：** 高权限模式可纳入统一循环，但进入时应立即提供醒目警示，并让用户能在下一次循环中离开该模式。

## 2. 已部署应用的证据

### OpenCode：自动模式与拒绝规则分层

- **事实：** OpenCode 的权限文档说明其配置决定行为是自动执行、请求批准还是阻止；`--auto` 会自动批准未被显式拒绝的请求。[source](https://opencode.ai/docs/permissions/)（访问日期：2026-08-10）。
- **事实：** 同一文档说明 auto mode 不会覆盖明确的 `deny` 规则，并指出 TUI 可通过 command palette 启用或关闭自动批准模式。[source](https://opencode.ai/docs/permissions/)（访问日期：2026-08-10）。

## 3. 机制与权衡

- **综合：** 用一个确定的环形顺序比多个隐藏入口更容易预测，但循环包含高权限模式时，单次误触可能比直接模式切换更敏感。
- **综合：** 高权限切换应只在 idle、无待决批准和无并发子任务时生效，避免改变已经在执行或等待用户授权的操作语义。
- **综合：** 警告是告知机制而不是隔离机制；真正的 deny、路径检查和沙箱边界必须由执行层保证。

## 4. 跨产品综合

- **综合：** 已公开资料支持把“自动批准”作为一个可见的会话交互模式，同时保留不可覆盖的拒绝规则。
- **综合：** 在没有可核验的其他产品快捷键证据时，不应把某个产品的具体按键或高权限循环顺序表述为行业标准。
